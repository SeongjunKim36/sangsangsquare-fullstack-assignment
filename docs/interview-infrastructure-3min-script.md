# 상상단 인프라 아키텍처 3분 설명

## 1. 한 줄 소개

이 프로젝트는 **Next.js 프론트엔드, NestJS API, SQLite**로 구성한 단일 풀스택 구조입니다.  
과제 범위에서는 실행과 검증이 단순해야 한다고 봐서, 핵심 흐름을 빠르게 확인할 수 있는 구조를 우선했습니다.

## 2. 현재 실행 구조

사용자는 브라우저로 Next.js 프론트엔드에 접속하고,  
프론트는 `NEXT_PUBLIC_API_URL` 기준으로 NestJS API를 호출합니다.  
API는 SQLite 파일을 직접 읽고 쓰면서 모임 조회, 신청, 선정 처리를 담당합니다.

로컬에서는 `pnpm dev`로 프론트와 서버를 함께 실행하고,  
초기 데이터는 `pnpm --filter server seed`로 준비합니다.

## 3. 왜 이런 구조를 선택했는가

과제에서 중요한 건 운영 인프라를 크게 꾸미는 것보다  
모집, 신청, 발표, 선정 결과 공개 흐름을 안정적으로 검증하는 것이라고 판단했습니다.

그래서

- DB는 SQLite로 단순하게 두고
- 인증은 세션 기반으로 두고
- 프론트와 서버도 설명하기 쉬운 구조로 유지했습니다.

대신 단순화하더라도 놓치지 않으려고,

- 개발 / 테스트 / 운영 환경 분기
- 제출용 DB와 E2E DB 분리
- GitHub Actions 기반 lint / build / e2e 검증

이 세 가지는 꼭 챙겼습니다.

## 4. Docker와 CI

Docker에서는 하나의 컨테이너 안에서 프론트와 서버를 함께 띄웁니다.  
컨테이너 시작 시 seed를 한 번 수행하고, 그다음 서버와 프론트를 같이 실행합니다.

GitHub Actions에서는

1. install
2. seed
3. web lint/build
4. server lint/build
5. server e2e

순서로 검증해서, 로컬에서 확인한 흐름을 저장소 기준으로도 다시 확인할 수 있게 했습니다.

## 5. 운영으로 확장한다면

운영으로 간다면 가장 먼저 바뀔 부분은 DB입니다.  
SQLite 대신 PostgreSQL 같은 중앙 DB로 옮기고, 필요하면 프론트와 서버 배포 단위도 분리할 수 있습니다.

다만 이 과제에서는 그 단계까지 가기보다,  
현재 요구사항을 안정적으로 검증할 수 있는 최소 구조를 먼저 만드는 데 집중했습니다.

## 6. 면접에서 강조할 포인트

- 단순히 기술을 줄세운 구조가 아니라, 과제 범위에 맞는 실행 구조를 선택했다는 점
- 단순화했지만 테스트 격리와 CI 검증은 놓치지 않았다는 점
- 현재 구조와 운영 확장 시 변화 지점을 구분해서 생각했다는 점
